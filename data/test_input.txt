# Data is deliberately engineered so all three currently-implemented
# alerts fire unambiguously by the time the Alerts section runs:
#   - PEAK_WINDOW_APPROACHING: Domaine Leroux and Chateau Reynard are
#     both built so their peak window opens ~98 days from "today"
#     (2026-09-25), inside the default 180-day lead time.
#   - LOW_STOCK_FAVORITE: Maison Belliard is added at quantity 1,
#     favorite = Y, and is never tasted/consumed afterward, so it
#     can't accidentally get bumped to 0 and flip to CONSUMED.
#   - STORAGE_CONDITION: Wine Rack A gets exactly one reading with
#     BOTH temperature and humidity out of range (tests the "two
#     distinct alerts for one location" case); Basement Cave gets
#     exactly one reading with only humidity out of range. Cellar
#     Fridge and Garage Overflow each get one healthy reading, for
#     contrast. Each flagged location gets only ONE reading total,
#     so there's no ambiguity about which reading is "most recent."
#
# Four real locations, five real bottles, five real tasting logs
# survive to the end. One throwaway location, one throwaway bottle,
# and one throwaway tasting log exercise the three Delete flows
# without touching any of the real data above.
#
# Lines starting with # are comments, skipped by InputHandler.
# "# --- TEST N ---" lines are also skipped but print a
# [DEBUG - STEP #N] marker in the console, for easy tracing.
